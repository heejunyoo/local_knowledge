## 결론

> **둘 다 그대로 간다. 새 리포도, 새 호스팅도 만들지 않는다.**
> 지금 손대야 하는 것은 플랫폼이 아니라 **방치된 브랜치 하나와 죽은 keepalive 하나**다.

| 결정 | 내용 |
|---|---|
| **D-1** | 개인비서는 `KnowledgeApp` 리포에서 계속한다. 새 리포를 만들지 않는다 |
| **D-2** | `ingreed` 는 **합치지 않는다.** 교차 프로젝트 RPC(제품 영양 공급자)로 남긴다 |
| **D-3** | Vercel Hobby 를 유지한다. **주기 실행은 Vercel Cron 이 아니라 Supabase `pg_cron`** 에 둔다 |
| **D-4** | `refactor/web-p0` → `main` 머지가 개인비서 확장의 **선행 조건**이다 |
| **D-5** | Supabase 가 정지됐다. keepalive 코드는 멀쩡하므로 **원인을 진단부터** 한다 (§2.3) |

## 1. 리포 — 왜 새로 만들지 않는가

### 1.1 옵션 비교

가중치 근거를 못 적는 축은 넣지 않았다.

| 기준 | 가중 | 가중 근거 |
|---|---|---|
| 재사용 자산 | **높음** | 이미 프로젝트 원칙(`PERSONAL_ASSISTANT_EXPANSION_PLAN.md` IB1·IB2)이 "새 SoT 전에 조립"을 선언했다 |
| 관심사·수명주기 분리 | 중 | ingreed 는 공개 서비스, 개인비서는 1인 사설 — 사용자·데이터 소유자가 다르다 |
| 무료 티어 여유 | 중 | ingreed DB 231MB / 500MB. 실제로 압박이 있다 |
| 1인 운영 표면 | 중 | 리포·배포·DB 가 늘수록 전부 혼자 감당한다 |

| 옵션 | 재사용 | 분리 | 티어 | 운영 | 판정 |
|---|---|---|---|---|---|
| **A. KnowledgeApp 계속** | ◎ | ○ | ○ | ◎ | **채택** |
| B. 개인비서 새 리포 | ✕ | ◎ | ○ | ✕ | 기각 |
| C. ingreed 와 모노레포 통합 | ○ | ✕ | ✕ | ○ | 기각 |

### 1.2 반증 시도 — A 를 깨보려 한 기록

| 깨보려 한 것 | 결과 |
|---|---|
| "Swift 모노레포가 웹 확장을 막지 않나" | **막지 않는다.** Vercel Root=`web` 으로 격리돼 있다. 다만 Mac 앱은 쓰기 동결(P0-8) 상태라 사실상 냉동 — 이건 리포를 가를 이유가 아니라 archive 판단 문제다 |
| "새 리포가 깨끗한 출발을 주지 않나" | **진다.** 버릴 수 없는 자산이 크다 — RPC 레지스트리 53개 메서드(`lib/rpc/dispatch.ts`), `diet-read.ts` 1111행, RLS(`004_rls.sql`), 매직링크 인증, 테스트 224개, ingreed 클라이언트. 새 리포는 이걸 다시 만들거나 통째로 import 해야 한다 |
| "ingreed 와 합치면 교차 프로젝트 복잡도가 사라지지 않나" | **사라지지 않고 옮겨간다.** ingreed 는 공개 데모(`ingreed.vercel.app`)에 앱인토스 미니앱까지 있는 별도 제품이다. 개인 건강 데이터를 같은 프로젝트에 넣으면 공개 서비스와 사설 데이터가 한 RLS 경계 안에 들어가고, 231MB 제품 DB 가 500MB 한도에서 개인 데이터를 잠식한다 |
| "그럼 왜 새 프로젝트를 만들고 싶었나" | **원인은 리포가 아니라 브랜치였다.** → §1.3 |

### 1.3 ⭐ 진짜 문제 — main 이 3.5주째 죽어 있다

```
main            9c8531e (2026-07-27) — docs 커밋 하나
refactor/web-p0 HEAD    — main 대비 +69 커밋, 0 behind
```

Vercel 이 이 브랜치를 프로덕션으로 보고 있다(`REFACTOR_STATUS.md` §레포 3개). 개인비서 확장을
여기에 또 얹으면 임시 브랜치가 영구 트렁크가 된다. **"새 프로젝트로 갈까"라는 감각의 실제
출처가 이것일 가능성이 높다** — 리포가 낡은 게 아니라 트렁크가 없는 것이다.

→ **D-4**: 개인비서 Phase 착수 전에 `refactor/web-p0` 를 `main` 에 머지하고 Vercel 프로덕션
브랜치를 `main` 으로 되돌린다. 이건 개인비서 작업이 아니라 그 앞의 정리다.

## 2. 호스팅 — 왜 Vercel 을 유지하는가

### 2.1 확인한 제약 (원문, 2026-08-20 열람)

| 항목 | Hobby | 출처 |
|---|---|---|
| Cron 최소 간격 | **1일 1회**, 정밀도 ±59분. 더 잦은 식은 **배포 자체가 실패** | <https://vercel.com/docs/cron-jobs/usage-and-pricing> (last_updated 2026-07-15) |
| 함수 실행시간 | 기본 **10s** / 최대 **60s** (2025-04-23 이전 배포·비 Fluid 기준) | <https://vercel.com/docs/limits> (last_updated 2026-08-03) |
| 월 사용량 | 호출 100만 · Fast Data Transfer 100GB · Active CPU 4시간 | 같은 문서 |
| Git 조직 리포 연결 | Hobby 팀은 **불가**(개인 소유 리포만) | 같은 문서 |

### 2.2 반증 시도

| 깨보려 한 것 | 결과 |
|---|---|
| "cron 1일 1회면 개인비서가 안 되지 않나" | **개인비서로 가면 실제로 막힌다**(리마인더·야간 확정·동기화). 하지만 떠날 이유는 아니다 — `pg_cron 1.6.4` 가 같은 Supabase 무료 티어에서 **실측 PASS** 돼 있고(`SUPABASE_FREE_TIER_CHECK_2026-07-27.md` 항목 3), 이미 `006_fasting_reminder_cron.sql` 로 써 본 뒤 `007` 에서 걷어낸 이력이 있다. → **D-3**: 스케줄러는 DB 쪽에 둔다 |
| "함수 10초면 RAG 답변이 잘리지 않나" | **경계 위에 있다.** `knowledge.ask` 는 LLM 호출이고 `knowledge.ask.fast` 가 따로 있는 것 자체가 이미 이 압력의 흔적이다. 다만 `maxDuration` 으로 60s 까지 올릴 수 있어 치명적이지 않다 — 올려두는 것을 후속 조치로 남긴다 |
| "Fly/Railway/자체 호스팅이 낫지 않나" | **기각.** 얻는 것은 cron 자유 하나인데 그건 pg_cron 으로 이미 해결된다. 1인이 런타임·TLS·배포를 떠안는 대가가 크다 |
| "그럼 지금 아픈 곳은 없나" | **있다.** → §2.3 |

### 2.3 ⭐ keepalive 는 돌지 않았다 — 코드 탓이 아니다

`web/vercel.json` 에 `/api/cron/keepalive` 가 하루 한 번 걸려 있는데 **Supabase 프로젝트는 실제로
일시정지됐다**(`.claude/specs/daily-grade/spec.md` §1 — `test:regression` 실행 불가).

**코드를 먼저 의심했다가 틀렸다.** 라우트는 `settings` 테이블에 실제 select 를 날리고
(`web/app/api/cron/keepalive/route.ts`), `CRON_SECRET` 도 Vercel Production 에 등록돼 있다
(`docs/ENV_VARS.md`, 2026-07-29). 고칠 코드가 없다.

남는 원인은 둘이고, **어느 쪽인지 로그를 봐야 안다.**

| 가설 | 왜 그럴듯한가 | 확인 방법 |
|---|---|---|
| **⑴ 크론이 아예 안 돌았다** | Vercel Cron 은 **Production 배포에서만** 실행된다. 이 리포의 프로덕션 브랜치가 `main` 이면, `main` 은 69커밋 뒤에 멈춰 있어 keepalive 라우트가 프로덕션에 없거나 낡은 채로 떠 있다 — §1.3 과 정확히 맞물린다 | Vercel 대시보드 Cron Jobs 실행 이력 (200 / 401 / 404) |
| **⑵ 하루 1회가 기준에 못 미친다** | Supabase 문서는 "**a few** user requests to the database **each day**"라고 쓴다. Hobby 크론 상한이 1일 1회라 이 경로로는 더 늘릴 수 없다 | 위 로그가 계속 200 인데도 정지됐다면 이쪽 |

**⑴ 이면 F-1(main 머지)이 그대로 처방이다.** ⑵ 라면 하루 여러 번 두드릴 채널이 따로 필요한데
(pg_cron 은 DB 내부 작업이라 "user request" 로 집계되지 않을 공산이 크다) **새 외부 서비스 도입은
오너 승인 대상**이라 여기서 정하지 않는다.

### 2.4 감도 확인 — 언제 이 결론이 뒤집히나

가중치를 흔들어 봤다. **"실시간 알림"을 최우선으로 두면 순위가 바뀐다.**
Vercel Hobby 에는 푸시 채널이 없고(액션플랜 §P5 가 Web Push 를 명시적으로 금지), pg_cron 은
DB 안에서만 돈다. **알림이 개인비서의 핵심 기능으로 승격되는 순간 이 결정을 다시 연다** —
그때의 선택지는 Vercel Pro($20/월)가 아니라 "알림 채널을 무엇으로 할지"가 먼저다.

그 외 가중치(재사용·티어·운영표면)는 어떻게 흔들어도 A/유지가 1위를 지켰다.
