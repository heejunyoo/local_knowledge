## 0. 왜 이 문서가 생겼나

2026-08-22 확인 결과 **건강 데이터가 2026-07-12 이후 41일간 한 건도 들어오지 않았다.**
`steps`·`active_energy_kcal` 은 칼럼이 생긴 뒤 **한 건도** 들어온 적이 없다.

원인은 경로 교체가 완결되지 않은 것이다.

```
예전(~2026-07-12)  워치 → 건강 앱 → 아이폰 Knowledge 앱을 열면 자동 동기
                   → Tailscale → 맥 Knowledge.app → diet.json
                   ※ 사용자가 누른 건 없었다. 앱을 여는 것이 트리거였다

이관(2026-07~08)   웹(Vercel+Supabase)으로 옮기면서 diet.json 을 한 번 마이그레이션했다.
                   지금 DB 의 healthkit 행은 전부 그때 옮겨온 것이고,
                   **그 뒤로 새 유입 경로를 아무도 연결하지 않았다**

지금               맥 앱은 쓰기 동결(P0-8), 아이폰 앱은 여전히 맥을 바라본다.
                   웹으로 들어오는 경로는 iOS 단축어뿐이다
```

**단축어를 매번 손으로 누르는 게 아니다.** 아래 §3 의 개인 자동화로 걸면 사용자 개입은 0 이다.

## 1. 엔드포인트

| | |
|---|---|
| URL | `https://hj-knowledge.vercel.app/api/health/ingest` |
| 메서드 | `POST` |
| 헤더 | `Authorization: Bearer <INGEST_API_TOKEN>` · `Content-Type: application/json` |
| 응답 | `{"accepted":n,"deduped":n,"received":n}` (실패 항목이 있으면 `errors[]` 추가) |

**토큰 값은 이 문서에도, 리포 어디에도 적지 않는다.** Vercel Production 환경변수에만 있다.
꺼내는 방법 둘 중 하나:

```bash
cd ~/IdeaProjects/KnowledgeApp/web
npx vercel env pull .env.production.local   # 파일에서 INGEST_API_TOKEN 확인 후 파일은 지운다
```

또는 Vercel 대시보드 → 프로젝트 `knowledge-web` → Settings → Environment Variables → `INGEST_API_TOKEN`.

## 2. 보낼 JSON

`samples` 배열 하나에 여러 건을 같이 실어도 된다.

```json
{
  "samples": [
    { "client_id": "steps-2026-08-22", "type": "metric", "ts": "2026-08-22T23:50:00+09:00", "steps": 9021, "source": "healthkit" },
    { "client_id": "sleep-2026-08-22", "type": "metric", "ts": "2026-08-22T12:00:00+09:00", "sleep_h": 7.1, "source": "healthkit" },
    { "client_id": "weight-2026-08-22", "type": "metric", "ts": "2026-08-22T07:30:00+09:00", "weight_kg": 85.2, "source": "healthkit" },
    { "client_id": "hk-workout-<샘플UUID>", "type": "workout", "ts": "2026-08-22T19:10:00+09:00", "kind": "걷기", "minutes": 25, "source": "healthkit" }
  ]
}
```

### ⚠ `client_id` 규칙이 동작을 가른다 (`web/lib/health-ingest.ts`)

| 필드 | 재전송하면 | 그래서 `client_id` 는 |
|---|---|---|
| `steps` · `active_energy_kcal` | **upsert — 값이 갱신된다** | `steps-YYYY-MM-DD` 처럼 **날짜 고정**. 하루 종일 몇 번을 다시 보내도 최신 누적값으로 덮인다 |
| `sleep_h` · `weight_kg` | **dedupe — 무시된다(`deduped++`)** | 날짜 고정이면 그날 **첫 값이 확정**된다. 하루 1회, 값이 굳은 뒤에 보내야 한다 |
| `workout` | dedupe | HealthKit 샘플 UUID 를 그대로 쓴다 — 운동은 하루 여러 건이라 날짜로 묶으면 1건만 남는다 |

`source` 는 `"healthkit"` 로 고정한다. 이 값이 `context: "healthkit"` 을 만들어
**아침 공복 체중(사용자가 직접 재는 값)과 절대 섞이지 않게** 한다. 이걸 바꾸면 체중 추세가 오염된다.

## 3. 단축어 만들기

아이폰 단축어 앱에서 **2개**를 만든다. 항목별로 따로 실패할 수 있어 하나에 몰지 않는다.

### 3-1. 「건강 → 클라우드 (아침)」 — 수면·체중

1. 새 단축어 → **건강 샘플 찾기**(Find Health Samples) 추가
   - 유형: **수면 분석**, 기간: 오늘(또는 어제 20시~오늘 12시), 정렬: 시작일
2. 수면 단계 샘플은 개별 구간으로 오므로 **합산이 필요하다**(`HEALTHKIT_SHORTCUTS_2026-08.md`).
   각 샘플의 지속시간을 더해 시간 단위로 바꾼다 → `sleep_h`
3. **건강 샘플 찾기** 하나 더 — 유형 **체중**, 최신 1건 → `weight_kg`
4. **사전(Dictionary)** 액션으로 §2 형태의 JSON 을 만든다
5. **URL의 콘텐츠 가져오기**(Get Contents of URL)
   - URL: §1
   - 방식: `POST` · 본문: `JSON` · 헤더에 `Authorization: Bearer <토큰>`

### 3-2. 「건강 → 클라우드 (자정 전)」 — 걸음수·활동에너지·운동

1. **건강 샘플 찾기** — 유형 **걸음 수**, 기간 오늘 → 값 **합계**(걸음수는 시간대별로 쪼개져 온다) → `steps`
2. 활동에너지도 같은 방식 → `active_energy_kcal`
   - ⚠ 이 항목은 단축어가 내보낼 수 있는지 **판정이 "불확실"** 이다(`HEALTHKIT_SHORTCUTS_2026-08.md`).
     유형 목록에서 안 잡히면 **그냥 빼고 진행한다.** 서버는 이 필드가 없어도 정상 동작하고,
     화면 경고(§5)도 이 필드로는 뜨지 않는다
3. **건강 샘플 찾기** — 운동, 오늘 → 건별로 `kind`·`minutes`·샘플 UUID
4. §2 형태로 POST

> 액션 이름은 iOS 버전에 따라 조금씩 다르다("건강 샘플 찾기"/"모든 건강 샘플 찾기"). 위 절차는
> 원문 확인된 1차 후기(`HEALTHKIT_SHORTCUTS_2026-08.md` 근거표)를 따른 것이고, **실제 유형 드롭다운은
> 실기기에서 확인해야 한다.**

## 4. 자동화 — 여기가 핵심이다

단축어 앱 → **자동화** 탭 → 새 자동화 → **시각**

| 자동화 | 시각 | 실행 |
|---|---|---|
| 3-1 (수면·체중) | 오전 8:00 | **「실행 전 확인」 끔** |
| 3-2 (걸음수·활동·운동) | 오후 11:50 | **「실행 전 확인」 끔** |

「실행 전 확인」을 켜 두면 알림을 탭해야 돌아간다 — 그게 켜져 있으면 이 설계는 실패한다.
시각 트리거는 확인 없이 즉시 실행을 지원한다(iOS 버전별 문구 차이는 실기기에서 확인).

## 5. 끊기면 화면이 말한다 (2026-08-22 구현)

41일 공백을 아무도 못 잡은 진짜 이유는 경로가 아니라 **끊긴 걸 알 방법이 없었다는 것**이다.

- `web/lib/domain/health-freshness.ts` — 채널별 마지막 유입으로 `fresh`/`stale`/`broken`/`never` 판정
- RPC `health.freshness` — 실제 DB 를 본다
- 홈 화면 최상단 배너 — `fresh` 가 아닐 때만, 등급 카드보다 **위에** 뜬다

| 상태 | 조건 | 근거 |
|---|---|---|
| `stale` | 36시간 이상 무유입 | 자동화가 하루 2회이므로 **연속 2회 실패** |
| `broken` | 7일 이상 | 그 상태로 일주일이면 설정이 깨진 것 |

감시 대상은 **수면·걸음수뿐**이다. 체중·운동은 사람이 안 하면 안 생기는 값이라(등급의
behavioral 결측과 같은 논리) 경고를 띄우지 않는다. 활동에너지는 §3-2 의 "불확실" 때문에 제외했다.

## 6. 설정 후 확인

1. 단축어를 손으로 한 번 실행 → 응답이 `{"accepted":n,...}` 인지 (401 이면 토큰, 400 이면 JSON 형태)
2. 홈 화면 새로고침 → **빨간 배너가 사라지면 유입이 살아난 것이다**
3. 다음날 아침, 자동화가 손대지 않고 돌았는지 배너로 확인

## 7. 이 문서가 답하지 않는 것

- **활동에너지 유형이 실제로 존재하는지** — 실기기 확인 필요(§3-2)
- **잠금 상태에서 시각 자동화가 항상 도는지** — 실기기 며칠 관찰 필요. 배너가 그걸 알려준다
- 수면 **단계별**(코어/렘/깊은잠) 분해 — 지금 스키마는 `sleep_h` 하나뿐이다
- 안정시심박 — 내보내기 가능하다고 확인됐지만 스키마·축이 없다
